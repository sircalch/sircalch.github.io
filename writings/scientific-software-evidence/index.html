Scientific Software Should Carry Its Evidence

An editorial essay on versions, tests, provenance and responsible claims in scientific software.

Original editorial writing. Not a peer-reviewed publication; no DOI.

Scientific software is often presented as if the code were the whole result. A repository is opened, a release is tagged, and a citation file is added. Those are useful acts, but they do not answer the most important question: what exactly should another person be able to know, reproduce or challenge from the software record?

A release is a boundary

A version number is more than a label. It identifies the source, documentation and behavior that belong together at a particular moment. If a repository reports one version while an archive or citation file reports another, the difference should be visible. It may be harmless, but it changes what a reader can reproduce and what a citation actually refers to.

The responsible record therefore distinguishes at least three things: the current development line, the latest public release and the latest archived release. These can be identical, but they should never be silently conflated.

Tests are evidence, not a universal verdict

Tests are one of the clearest ways for software to report what its authors expect to remain true. They can expose regressions, document examples and make a release auditable. They do not, by themselves, prove that a scientific method is valid, that a model answers a particular question or that a tool is ready for every use.

That distinction is not a weakness. It is a better description of what the evidence supports. A project can report a passing test suite while still marking benchmark design, domain limitations, external validation and independent replication as open questions.

Provenance is part of the scientific interface

Users need more than a download link. They need to know where a release came from, which license applies, whether an archive contains the same version, how to cite it and which claims are documented by source code rather than by independent evaluation.

This is why a useful software page connects the repository, release, archive, citation metadata, documentation and limitations. The links form a small provenance graph. They let a reader move from a readable explanation to the exact artifact that supports it.

Reproducibility includes the limits

Reproducibility is sometimes reduced to sharing code. Code is essential, but a reproducible record also needs a defined scope. Which version was used? Which command was run? What output should be expected? Which failures are known? What has not been tested?

Writing the limits down prevents a common mistake: turning a successful example into a general promise. A careful software record says what was observed, what was verified locally, what remains self-reported and what requires a different kind of evidence.

An archive should preserve distinctions

An intellectual archive becomes useful when it keeps different objects connected without making them interchangeable. A software release is not a paper. A DOI is not automatically peer review. A draft is not a publication. A project page is not a substitute for a canonical repository.

The archive can still connect these objects. It can show that a release belongs to a project, that a paper cites a version, or that a note explains a method. The connection becomes trustworthy when each object keeps its own status, date, source and permission boundary.

A practical standard

Before presenting a scientific software project as finished, ask five simple questions:

  1. What exact version is being described?
  2. Which source or archive is canonical for that version?
  3. What evidence has actually been run or inspected?
  4. Which claims remain outside that evidence?
  5. What should a future reader cite, reproduce or review?

These questions do not make software less ambitious. They make its ambition legible. Scientific software can be exploratory, incomplete and still valuable, provided the public record is precise about where the work stands.
